# main 브랜치 보호 규칙

이 문서는 GitHub Rulesets 적용 이후 `main` 브랜치 변경 방식을 정리합니다.

## 1. 기본 원칙

`main` 브랜치는 항상 실행 가능하고 배포 가능한 상태로 유지합니다.

따라서 코드뿐 아니라 문서와 설정 파일도 `main` 브랜치에서 직접 수정하지 않습니다.

대상 예시는 다음과 같습니다.

- `README.md`
- `docs/*`
- `.github/*`
- 프로젝트 설정 파일

## 2. 문서 수정 흐름

문서 수정도 작업 브랜치와 Pull Request를 통해 반영합니다.

```txt
1. Issue 생성
2. docs/이슈번호-작업명 브랜치 생성
3. 문서 수정
4. Commit 작성
5. Pull Request 생성
6. 리뷰 후 main에 병합
7. 작업 브랜치 정리
```

예시:

```txt
Branch: docs/19-rulesets-document-flow
Commit: docs: main 보호 규칙 문서 추가 (#19)
PR: [docs] Rulesets 적용 후 문서 수정 흐름 명시
```

## 3. 문서 PR 확인 기준

문서 PR은 코드 변경 PR보다 가볍게 리뷰할 수 있습니다.

다만 아래 항목은 확인합니다.

- 기존 문서의 규칙과 충돌하지 않는가
- 팀원이 이해하기 쉬운가
- 현재 운영 방식과 맞는가
- 오탈자가 없는가

문서 수정처럼 배포 확인이 필요하지 않은 작업은 PR 본문에 아래처럼 작성합니다.

```md
## 배포 확인

- 해당 없음: 문서 수정
```

## 4. 운영 기준

단순 오탈자 수정처럼 Issue를 만들기 애매한 경우에도 가능하면 문서 수정용 브랜치를 만들고 PR 기록을 남깁니다.

이 규칙의 목적은 작업을 복잡하게 만드는 것이 아니라, `main` 브랜치의 안정성과 협업 기록을 함께 지키는 것입니다.
